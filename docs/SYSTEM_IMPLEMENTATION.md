# System Implementation

## A. Logical Architecture and Topology

The proposed system architecture is designed as a multi-layered topology that bridges the gap between the physical industrial assets and the digital management interfaces, adhering to the RAMI 4.0 reference model. The architecture is stratified into three primary logical layers: the **Physical World/Field Layer**, the **Edge Layer**, and the **Cloud/Application Layer**.

At the **Physical World/Field Layer**, the core component is the SCARA robot, which operates as the primary data source. This layer includes the integrated OPC UA server embedded within the robot's controller, responsible for exposing real-time industrial variables such as joint positions, temperature, and operational status. The communication backbone at this level relies on the **OPC UA (Open Platform Communications Unified Architecture)** protocol (specifically `opc.tcp`), ensuring robust, platform-independent data exchange directly from the shop floor.

The **Edge Layer** acts as the critical intermediary for data acquisition, processing, and local persistence. It hosts the asynchronous Python-based acquisition client (`client_asyncua.py`), which polls the field devices via OPC UA. This layer performs the essential task of semantic mapping, converting raw PLC data into the standardized **Asset Administration Shell (AAS)** structure. It also manages local persistence using a dual-strategy approach: a lightweight **SQLite** database for historical time-series data and atomic JSON file operations for maintaining the latest state snapshots (`latest_data.json`). A local OPC UA server mirror is also deployed here to allow external systems to consume pre-processed data without overloading the physical robot's controller.

The **Cloud/Application Layer** provides the user interfaces and high-level API services. It is built upon a hybrid backend architecture utilizing **FastAPI** for high-performance robot data retrieval and **Flask** for handling authentication and legacy HR system integration. These services expose data via **HTTP/REST** APIs, serving JSON payloads to the frontend. The presentation layer is a Single Page Application (SPA) developed with **React**, **Vite**, and **TypeScript**, offering real-time dashboards and historical data analysis. The interoperability within this layer and across the system is guaranteed by the rigorous use of standard protocols, creating a seamless "backbone network" that transitions from industrial OPC UA at the edge to web-standard HTTP/REST at the application level.

## B. Implementation Flow and Processing

The system's operation follows a strictly defined sequential data processing pipeline, ensuring data integrity and semantic consistency from acquisition to visualization.

**Step 1: Data Acquisition and Modeling.** The process initiates with the `client_asyncua.py` module, which establishes a secure connection to the robot's OPC UA server. Guided by a configuration map (`config_opcua.json`), the client cyclically polls specific nodes. This step is not merely data copying; it involves an immediate semantic annotation where raw node IDs are mapped to human-readable AAS submodel elements (e.g., mapping `ns=4;s=...` to `OperationalData.JointPosition`).

**Step 2: Parsing and Conversion.** Upon acquisition, data undergoes a rigorous parsing and type coercion process. The system handles the conversion of OPC UA specific data types (e.g., `LocalizedText`, `ExtensionObject`) into standard Python primitives and subsequently into JSON-serializable formats. This phase ensures that complex industrial data structures are flattened or structured appropriately for the AAS schema. The system employs a custom mapper (`opcua_to_json_mapper.py` logic) to align the incoming data with the standardized AAS submodel definitions stored in `aas-submodels/*.json`, ensuring that the digital twin remains a faithful representation of the physical asset.

**Step 3: Data Exchange and Persistence.** The processed data is then dispatched to multiple destinations to support different consumption patterns. For real-time monitoring, the system performs atomic writes to `latest_data.json`, ensuring that the local OPC UA mirror and the dashboard always have access to the most current state without race conditions. Simultaneously, for historical analysis, data is normalized and inserted into the SQLite database. The system ensures semantic interoperability by strictly adhering to JSON standards for all data exchange interfaces and supports the export of the entire digital twin state as an **AASX** package (ZIP archive containing XML/JSON definitions), facilitating the transfer of the asset's digital representation between different Industry 4.0 compliant systems.

## C. Technical Specifications of Hardware and Software

The implementation leverages a robust, open-source technology stack selected for performance, scalability, and industry support. The core logic is implemented in **Python 3.x**, utilizing the **asyncua** library for asynchronous OPC UA communication, ensuring efficient non-blocking I/O operations suitable for high-frequency data polling. Data manipulation and analysis are powered by **NumPy** and **Pandas**, providing the necessary computational efficiency for handling time-series data. The backend services are containerized and orchestrated, running on a **Linux-based Edge** environment, utilizing **FastAPI** and **Flask** frameworks to provide a scalable RESTful API surface.

For persistence, the system employs **SQLite** as a lightweight, serverless relational database, optimized for edge deployments where full-scale database servers might be resource-prohibitive. The database schema is designed to store both normalized submodel snapshots and high-resolution time-series data. The frontend application is built with **React 18** and **TypeScript**, leveraging **Vite** for optimized build performance and **Recharts** for rendering interactive data visualizations. The entire stack is designed to be deployment-agnostic, capable of running on industrial PCs (IPCs) or virtualized edge servers, with **Docker** support implied for consistent environment reproduction.
